v0.7.0 — provider layer: GCP behind providers/, groundwork for other targets

Why: the installer should later also run against other targets (first:
existing hosts over SSH, later other clouds). Everything cloud-specific now
sits behind one provider interface, so a new target is a new file in
providers/ instead of edits all over the installer. GCP is the only
provider and its behaviour is unchanged.

2026-10-15 — GCP moved behind providers/ (no behaviour change)
- New required folder providers/: common.sh (provider_<op> dispatch,
  provider selection, parameter checks) and gcp.sh (every gcloud call of the
  installer). install.sh refuses to start, and destroy.sh refuses to delete,
  when the folder is missing, with the git command that restores it.
  Copying the installer by hand: copy the whole folder, not only *.sh.
- Moved unchanged into providers/gcp.sh: GCP login and configuration checks,
  the project/region/zone/network/subnet questions, machine type selection,
  Ubuntu image check, VM/disk/firewall creation and their resume checks,
  SSH and file copy (same gcloud arguments, keep-alive and exit-255 retry),
  IP lookups, the gcloud commands shown in HOW TO RESOLVE boxes, the
  deletions in destroy.sh and the clean-up by VM name. capacity-fallback.sh
  remains the GCP stockout fallback. The data-disk path on the VM comes from
  the provider (GCP: /dev/disk/by-id/google-<device>, as before).
- Provider selection: a deployment recorded in the folder keeps its
  provider. .install-state.json now also records "provider" (a state file
  from an older version is treated as GCP). Without a recorded deployment
  the provider comes from INSTANA_PROVIDER, otherwise gcp. A different or
  unsupported provider stops with HOW TO RESOLVE naming both values and
  where they came from; it never switches silently. A PROVIDER variable in
  the shell environment has no effect.
- Parameter checks for the coming --config option: provider_param_keys,
  provider_validate_param (format only, no gcloud call) and PROVIDER_SCOPE/
  REGION/LOCATION/NETWORK/SUBNET as aliases of the GCP_* parameters.
- Tests: new test-destroy.sh (delete order and exact gcloud delete
  commands, confirmation phrase, dry-run, refusal of unusable state files),
  test-provider-contract.sh (every provider implements every operation;
  provider selection rules; parameter checks) and test-gcp-provider.sh
  (exact gcloud arguments of SSH, probes, copies and IP lookups). The other
  tests copy the whole folder instead of a fixed file list. The dry-run
  output of all test-dry-run cases is unchanged.

2026-10-15 — Parameters from a JSON file (--config, config-generator.html)
Why: a lab is often prepared ahead of time or repeated with small changes;
answering 25 questions each time is slow and error-prone. The parameters
can now be prepared in a browser page and handed to the installer, which
still checks every value and asks only what is missing or wrong.
- config-generator.html (works offline from file://) builds the input file
  (schema instana-installer-input, schema_version 1). examples/ holds input
  files for every case, with README.txt describing the expected behaviour.
- New input-config.sh. ./install.sh --config FILE, or "import them from a
  JSON file" in the new menu "How do you want to provide the deployment
  parameters?" (enter now / import / reuse saved / edit saved). The menu
  replaces the separate "Previous configuration found" question for a new
  deployment; --resume is unchanged.
- Each value from the file gets the same check as a typed answer. A summary
  shows ok / ask (with the reason) / skip. A missing or invalid value is
  explained, then asked as usual; the bad value is never offered as default.
- Without a terminal (--config with stdin not a terminal) the installer stops
  before the first question and lists every missing or invalid value with
  what it is for and a valid example (HOW TO RESOLVE).
- Keys and admin password: asked hidden by default; may come from the file
  (made owner-only, 600, with a warning) or from INSTANA_DOWNLOAD_KEY,
  INSTANA_AGENT_KEY, INSTANA_SALES_KEY, INSTANA_ADMIN_PASSWORD. Never shown or
  logged. After Start the installer offers to blank them in the file; nothing
  is changed without yes.
- PROVIDER_SCOPE/REGION/LOCATION/NETWORK/SUBNET in a file are accepted as
  GCP_* aliases; two different values for one setting are chosen in a
  terminal or listed without one. GCP_REGION follows from GCP_ZONE when only
  the zone is given. Unknown keys are ignored with a "did you mean" hint.
  PROVIDER "ssh" stops with an explanation (existing hosts come next).
- Versions in the file are taken when the live list offers them; otherwise
  the list is shown. Air-gapped: versions come from the package.
- Plan for a new deployment: Y start, E change one value (every other value
  is kept and re-checked, then the plan is shown again), S save the
  parameters to a new input file without keys, N cancel.
- ./install.sh --export-config [FILE] writes the parameters saved in this
  folder (.install-config.json) as an input file without keys.
- A recorded three-node deployment in the folder still leads to the resume /
  set-aside question; resume from a file is refused with the command to use
  (./install.sh --resume). --config together with --resume is refused.
- Three-node no longer asks the machine size: the lab supports only the
  fixed small size (3x n2-standard-16), so the question could only lead to a
  later stop.
- Typed VM names, GCP region, zone, network and subnet are now checked when
  entered (re-asked at once instead of stopping later).
- Tests: new test-config-file.sh (20 cases on examples/). test-dry-run.sh:
  inputs start with the menu answer, three-node size answer removed;
  assertions unchanged. Dry-run output differs only by the menu, the E/S
  lines of the plan and the fixed-size line for three-node.

2026-10-15 — Install on existing hosts over SSH (PROVIDER ssh)
Why: support cases and customer environments often have their own machines
(on-prem, another cloud). The installer now installs on 1 or 3 existing
Ubuntu hosts over plain SSH, with the same phases 6-12 as on GCP. It never
creates, deletes, or reboots a host without confirmation.
- New providers/ssh.sh. Start with INSTANA_PROVIDER=ssh ./install.sh, or a
  file with "PROVIDER": "ssh" (config-generator.html: "Existing hosts").
- Questions: host(s), SSH user, key, port. Ubuntu image, SSH source CIDR
  and machine size are not asked. Each host is read once over SSH
  (read-only): OS, CPU, RAM, size of /, sudo, k3s, firewalld, disks.
  Names default to the hosts' own names. One dedicated disk per Instana data
  directory is chosen from the unused whole disks that are large enough;
  the stable /dev/disk/by-id path is stored, never /dev/sdX.
- SSH key with a passphrase: must be in ssh-agent; in a terminal the
  installer runs ssh-add once (ssh-add asks). The passphrase is never read,
  stored or logged. Without an agent it stops with the ssh-agent commands.
- Phase 3 checks every host: Ubuntu 22.04/24.04, x86_64, CPU/RAM minimum,
  / at least 100 GB (IBM; three-node below 270 GB only warns), passwordless
  sudo, no active firewalld (stop with the disable command; the installer
  never disables it), no existing k3s, three-node sshd on port 22, and on
  resume the same machine-id as at the start. Phase 4 re-verifies the
  chosen disks (state keys hostdisk_*). Phase 5 lists the ports the network
  must allow and asks to confirm them (or NETWORK_RULES_CONFIRMED in a file).
- After "Start now?" the changes on the hosts (kernel + reboot, UFW, root
  SSH between nodes, disk formatting, k3s) are confirmed separately, always
  in a terminal; an input file cannot pre-approve them.
- Every stop says what was found on which host, why it blocks the
  installation, the exact fix and how to continue (host_stop).
- UFW keeps the configured SSH port open (GCP: 22 as before).
- --destroy for ssh removes only the local state and lists what stays on
  the hosts. A known_hosts file of its own (.ssh-known-hosts) makes a
  changed host key a hard stop.
- config-generator.html: the "not available yet" note is gone; three nodes
  ask only the disks the layout uses (node 0 objects, node 1 data, metrics,
  analytics); /dev/sdX is refused. --config: GCP-only keys are ignored with
  the reason for ssh.
- GCP behaviour and output are unchanged (provider hooks with the original
  texts; the dry-run output of the GCP cases is identical).
- Tests: test-ssh-provider.sh, test-ssh-host-checks.sh (each stop asserts
  what/why/fix/continue), test-ssh-disk-map.sh, ssh cases in test-dry-run,
  test-config-file and test-destroy; fakes in test-ssh-lib.inc.
