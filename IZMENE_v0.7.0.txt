v0.7.0 — provider layer: GCP behind providers/, groundwork for other targets

Why: the installer should later also run against other targets (first:
existing hosts over SSH, later other clouds). Everything cloud-specific now
sits behind one provider interface, so a new target is a new file in
providers/ instead of edits all over the installer. GCP is the only
provider and its behaviour is unchanged.

2026-10-15 — GCP moved behind providers/ (no behaviour change)
- New required folder providers/: common.sh (provider_<op> dispatch,
  provider selection, parameter checks) and gcp.sh (every gcloud call of the
  installer). install.sh refuses to start, and destroy.sh refuses to delete,
  when the folder is missing, with the git command that restores it.
  Copying the installer by hand: copy the whole folder, not only *.sh.
- Moved unchanged into providers/gcp.sh: GCP login and configuration checks,
  the project/region/zone/network/subnet questions, machine type selection,
  Ubuntu image check, VM/disk/firewall creation and their resume checks,
  SSH and file copy (same gcloud arguments, keep-alive and exit-255 retry),
  IP lookups, the gcloud commands shown in HOW TO RESOLVE boxes, the
  deletions in destroy.sh and the clean-up by VM name. capacity-fallback.sh
  remains the GCP stockout fallback. The data-disk path on the VM comes from
  the provider (GCP: /dev/disk/by-id/google-<device>, as before).
- Provider selection: a deployment recorded in the folder keeps its
  provider. .install-state.json now also records "provider" (a state file
  from an older version is treated as GCP). Without a recorded deployment
  the provider comes from INSTANA_PROVIDER, otherwise gcp. A different or
  unsupported provider stops with HOW TO RESOLVE naming both values and
  where they came from; it never switches silently. A PROVIDER variable in
  the shell environment has no effect.
- Parameter checks for the coming --config option: provider_param_keys,
  provider_validate_param (format only, no gcloud call) and PROVIDER_SCOPE/
  REGION/LOCATION/NETWORK/SUBNET as aliases of the GCP_* parameters.
- Tests: new test-destroy.sh (delete order and exact gcloud delete
  commands, confirmation phrase, dry-run, refusal of unusable state files),
  test-provider-contract.sh (every provider implements every operation;
  provider selection rules; parameter checks) and test-gcp-provider.sh
  (exact gcloud arguments of SSH, probes, copies and IP lookups). The other
  tests copy the whole folder instead of a fixed file list. The dry-run
  output of all test-dry-run cases is unchanged.

2026-10-15 — Parameters from a JSON file (--config, config-generator.html)
Why: a lab is often prepared ahead of time or repeated with small changes;
answering 25 questions each time is slow and error-prone. The parameters
can now be prepared in a browser page and handed to the installer, which
still checks every value and asks only what is missing or wrong.
- config-generator.html (works offline from file://) builds the input file
  (schema instana-installer-input, schema_version 1). examples/ holds input
  files for every case, with README.txt describing the expected behaviour.
- New input-config.sh. ./install.sh --config FILE, or "import them from a
  JSON file" in the new menu "How do you want to provide the deployment
  parameters?" (enter now / import / reuse saved / edit saved). The menu
  replaces the separate "Previous configuration found" question for a new
  deployment; --resume is unchanged.
- Each value from the file gets the same check as a typed answer. A summary
  shows ok / ask (with the reason) / skip. A missing or invalid value is
  explained, then asked as usual; the bad value is never offered as default.
- Without a terminal (--config with stdin not a terminal) the installer stops
  before the first question and lists every missing or invalid value with
  what it is for and a valid example (HOW TO RESOLVE).
- Keys and admin password: asked hidden by default; may come from the file
  (made owner-only, 600, with a warning) or from INSTANA_DOWNLOAD_KEY,
  INSTANA_AGENT_KEY, INSTANA_SALES_KEY, INSTANA_ADMIN_PASSWORD. Never shown or
  logged. After Start the installer offers to blank them in the file; nothing
  is changed without yes.
- PROVIDER_SCOPE/REGION/LOCATION/NETWORK/SUBNET in a file are accepted as
  GCP_* aliases; two different values for one setting are chosen in a
  terminal or listed without one. GCP_REGION follows from GCP_ZONE when only
  the zone is given. Unknown keys are ignored with a "did you mean" hint.
  PROVIDER "ssh" stops with an explanation (existing hosts come next).
- Versions in the file are taken when the live list offers them; otherwise
  the list is shown. Air-gapped: versions come from the package.
- Plan for a new deployment: Y start, E change one value (every other value
  is kept and re-checked, then the plan is shown again), S save the
  parameters to a new input file without keys, N cancel.
- ./install.sh --export-config [FILE] writes the parameters saved in this
  folder (.install-config.json) as an input file without keys.
- A recorded three-node deployment in the folder still leads to the resume /
  set-aside question; resume from a file is refused with the command to use
  (./install.sh --resume). --config together with --resume is refused.
- Three-node no longer asks the machine size: the lab supports only the
  fixed small size (3x n2-standard-16), so the question could only lead to a
  later stop.
- Typed VM names, GCP region, zone, network and subnet are now checked when
  entered (re-asked at once instead of stopping later).
- Tests: new test-config-file.sh (20 cases on examples/). test-dry-run.sh:
  inputs start with the menu answer, three-node size answer removed;
  assertions unchanged. Dry-run output differs only by the menu, the E/S
  lines of the plan and the fixed-size line for three-node.

2026-10-15 — Install on existing hosts over SSH (PROVIDER ssh)
Why: support cases and customer environments often have their own machines
(on-prem, another cloud). The installer now installs on 1 or 3 existing
Ubuntu hosts over plain SSH, with the same phases 6-12 as on GCP. It never
creates, deletes, or reboots a host without confirmation.
- New providers/ssh.sh. Start with INSTANA_PROVIDER=ssh ./install.sh, or a
  file with "PROVIDER": "ssh" (config-generator.html: "Existing hosts").
- Questions: host(s), SSH user, key, port. Ubuntu image, SSH source CIDR
  and machine size are not asked. Each host is read once over SSH
  (read-only): OS, CPU, RAM, size of /, sudo, k3s, firewalld, disks.
  Names default to the hosts' own names. One dedicated disk per Instana data
  directory is chosen from the unused whole disks that are large enough;
  the stable /dev/disk/by-id path is stored, never /dev/sdX.
- SSH key with a passphrase: must be in ssh-agent; in a terminal the
  installer runs ssh-add once (ssh-add asks). The passphrase is never read,
  stored or logged. Without an agent it stops with the ssh-agent commands.
- Phase 3 checks every host: Ubuntu 22.04/24.04, x86_64, CPU/RAM minimum,
  / at least 100 GB (IBM; three-node below 270 GB only warns), passwordless
  sudo, no active firewalld (stop with the disable command; the installer
  never disables it), no existing k3s, three-node sshd on port 22, and on
  resume the same machine-id as at the start. Phase 4 re-verifies the
  chosen disks (state keys hostdisk_*). Phase 5 lists the ports the network
  must allow and asks to confirm them (or NETWORK_RULES_CONFIRMED in a file).
- After "Start now?" the changes on the hosts (kernel + reboot, UFW, root
  SSH between nodes, disk formatting, k3s) are confirmed separately, always
  in a terminal; an input file cannot pre-approve them.
- Every stop says what was found on which host, why it blocks the
  installation, the exact fix and how to continue (host_stop).
- UFW keeps the configured SSH port open (GCP: 22 as before).
- --destroy for ssh removes only the local state and lists what stays on
  the hosts. A known_hosts file of its own (.ssh-known-hosts) makes a
  changed host key a hard stop.
- config-generator.html: the "not available yet" note is gone; three nodes
  ask only the disks the layout uses (node 0 objects, node 1 data, metrics,
  analytics); /dev/sdX is refused. --config: GCP-only keys are ignored with
  the reason for ssh.
- GCP behaviour and output are unchanged (provider hooks with the original
  texts; the dry-run output of the GCP cases is identical).
- Tests: test-ssh-provider.sh, test-ssh-host-checks.sh (each stop asserts
  what/why/fix/continue), test-ssh-disk-map.sh, ssh cases in test-dry-run,
  test-config-file and test-destroy; fakes in test-ssh-lib.inc.

2026-10-15 — Existing hosts: review fixes (security and safety)
- Saved SSH values (.install-config.json on reuse, edit, --resume) get the
  same checks as typed answers, and phase 2 checks them again before the
  first ssh call; a bad value stops with an explanation and is never used.
  ssh gets the user with -l and the host after "--" (scp: -o User= and
  "--"), so no value can become an ssh option. Disk links reported by a
  host are used only when they are plain /dev/disk/by-id or by-path names.
- Before a disk without a filesystem signature is formatted on an existing
  host, its first and last MiB are read; anything but zeros stops with
  the exact commands to inspect and, if wanted, wipe it (GCP unchanged).
- The first connection to a host shows the host key that is trusted from
  then on. The host identity for --resume falls back to the DMI product
  UUID when /etc/machine-id is missing; without any identity the run stops.
- Tests: hostile saved values (test-ssh-hostile-config.sh), disks that are
  mounted, partitioned or LVM members are never offered, GCP UFW keeps 22
  with SSH_PORT exported, GCP destroy ignores hostdisk_* keys, the zero
  check runs before mkfs.
- Follow-up: the last MiB is read by byte offset, so the very end of a disk
  whose size is not a multiple of 1 MiB (where a GPT backup header sits) is
  checked too; a failed read stops. The copy-paste commands in HOW TO
  RESOLVE boxes shell-quote the key and file paths. Tests: the three-node
  mount step, a failing read, and a 5.5 MiB image with data in its last
  half MiB.

2026-10-19 — Existing hosts: findings from the first real run (ssh-test-1)
- A new deployment with another provider in a folder that records one: in
  a terminal (not --resume) the installer shows the recorded deployment
  (provider, project/zone or hosts, VMs, last phase, cost reminder for GCP)
  and offers to continue it, to set its files aside (renamed, nothing
  deleted) and start the new one, or to cancel. --resume and runs without a
  terminal still stop; the stop also names ./install.sh --destroy.
- Existing-host runs no longer show GCP wording before the provider is
  resolved: the dry-run notice, the first checklist and the phase 1 text
  follow INSTANA_PROVIDER or the recorded provider. The plan does not show
  a GCP image name as "Ubuntu version" (each host's OS is listed instead).
- After a successful run inside screen the outer terminal prints the
  duration, ./install.sh --report and the log path, not only
  "[screen is terminating]".
- The "SSH login failed" stop and README section 6 explain two real
  causes: running the installer as a different Linux user than the key
  owner, and GCP OS Login (enable-oslogin=TRUE) ignoring metadata keys.
- GCP dry-run output is unchanged.
- Host address: on a Google Cloud control machine with gcloud, the running
  VMs of the project are offered as a numbered list (name, zone, internal
  IP; this machine and hosts already chosen left out, its own zone first),
  plus "enter another address". A saved address is the default instead;
  without gcloud, or if listing fails, the address is typed (never a stop).
  The SSH user defaults to "ubuntu" (Ubuntu cloud images).
- Set-aside never overwrites an earlier copy from the same second, and if
  the second file cannot be moved the stop says exactly what was already
  moved. A dry-run does not offer "continue" (it needs --resume); "continue"
  together with --config is refused. Before phase 1 the recorded provider
  wins over INSTANA_PROVIDER, and --export-config always writes the
  recorded provider. The host list is not shown when gcloud has no project.

2026-10-19 — Bug fixes from the UX review
- Existing hosts, data disks: roles are asked largest first (three-node
  node 1: analytics, metrics, data), and only disks that still leave a
  disk for every remaining role are offered; when a host cannot hold all
  its roles at all, the run stops before the first pick, listing the disks
  found and the sizes needed. Before, picking a large disk for "data" could
  make "analytics" impossible and lose every answer.
- Existing hosts, public IP: a private host address (RFC 1918, 100.64/10)
  is no longer offered as the public IP. On Google Cloud the instance's
  external IP is looked up (read-only, optional); otherwise the address is
  asked at the end with a note that /etc/hosts lines with a private address
  work only inside that network. Single-node derives this from the address.
- destroy (preview) no longer asks for the DELETE phrase (also GCP).
- A stop says "--resume" only when something was already created; before
  that it says nothing was created and to run ./install.sh again (also GCP).
- A dry-run ends with "Dry-run complete — nothing was created or changed"
  instead of "Installation Complete!" with "DRY-RUN" as IP and /etc/hosts
  lines (also GCP; the rest of the GCP dry-run output is unchanged).
- Disk prompts say "the Instana <role> directory" (no more "data data").
- Fix: changing any value at the plan ("E") no longer stops an existing-
  host deployment whose disks exactly cover the roles (the disk check now
  counts the host's own chosen disks as available). The disk filter keeps
  every other open role of the host possible, in whatever order roles are
  filled. Loopback (127/8) and link-local (169.254/16) addresses are never
  offered as the public IP.

2026-10-19 — UX v2, step 2: "<" goes back to the previous question
Why: a wrong or unknown answer (an IP address, a size) could only be fixed
by cancelling the whole run.
- The questions run as steps (collect_parameters → wiz_run). Answering "<"
  re-asks the previous question that was really asked; every later question
  is then asked again with its earlier answer as the Enter default
  ("[earlier] (< = back)"; pick lists "Select [1-2, Enter = 1, < = back]").
- A changed earlier answer clears what depends on it: topology → install
  type, names, size, (existing hosts: host addresses and disks); install type
  → size and disks; connectivity → package and versions; download key →
  versions; TLS mode → certificate paths. These are then asked again.
- Keys and password: "<" goes back; Enter keeps the one typed before.
- "<" at the first question goes back to the parameter-source menu; "<" at
  the JSON file path too. In a run from a file, values from the file are not
  "previous questions": "<" at the first question that is asked says where
  they come from and to change them with E at the plan.
- Plan E: "<" at the value keeps it ("... was not changed; back to the plan").
- "<" is never stored as a value. There is no "<" after Start, inside the
  air-gapped package menu, the version lists, the host/login block and the
  disk choice yet (next steps). "Edit saved parameters" now also offers the
  saved choice as the Enter default in pick lists.
- Unit, agent key and sales key got their own one-line hint (each question
  can now be reached on its own with "<").
- New test-nav-back.sh. Dry-run output: only the new hint lines.

2026-10-19 — UX v2, step 3 (changes the GCP flow): location in one block

- The VM name is checked against the VMs that already exist in the zone

- Runs from a file and E at the plan still ask single values (only what is

- Tests: test-dry-run.sh inputs (location = one Enter; no Ubuntu/size

2026-10-19 — UX v2, step 4: existing hosts — hosts first, login found, retry
Why: a wrong or unknown address, user or key used to stop the run in phase 1
and every answer was lost.
- Typed answers start with the host(s): a list of the running VMs of the
  gcloud project (name, internal and external IP, zone, machine type; the
  control machine is never listed) and of the Host entries in ~/.ssh/config,
  or typed addresses (host:port for another SSH port). 1 host = single-node,
  3 hosts = three-node (node 0 first); the topology is not asked.
- The login is found by trying the local private keys (agent-loaded and
  passphrase-free first; passphrase keys that are not in ssh-agent are
  skipped and named) with the users ubuntu and the local login name, at most
  6 tries of 5 s on the first host. "Use detected login" is confirmed with
  Enter, c changes user/key/port, < goes back.
- The read-only host checks (OS, CPU, RAM, sudo, Kubernetes, firewalld,
  disks) run right after the login and are shown as a table.
- Any failure (no answer, port closed, key refused, changed host key, a
  failed check) is explained with an "ssh -v" command and offers: re-enter
  the address / choose from the list / change the login / check again /
  cancel — no stop, no lost answers.
- Private or public addresses are derived from the address (also
  three-node; no more "false/true" question). Node names are the hosts' own
  names (made unique), not asked; E at the plan changes them.
- The install type is suggested from CPU, RAM and the unused disks, with
  the reason; production on a host that is too small is explained and
  asked again.
- Changing the hosts with "<" re-asks what depends on them (login check,
  names, disks, type); facts read with the same login are reused.
- Runs from a file keep the earlier per-value questions.
- Tests: new test-ssh-login-flow.sh (10 cases); test-dry-run.sh existing-host
  inputs (hosts first, login = Enter); the fake ssh can refuse a user or a key.
