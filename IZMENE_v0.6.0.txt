v0.6.0 — resilient installer: survives lost connections, always shows progress,
always says what to do next

This release collects everything added since v0.5.7 (19–29 September) and
was proven on real GCP deployments: single-node online (25.09), three-node
online (22.09) and three-node resume after a lost connection (29.09: the
connection dropped in the last phase after stanctl up had succeeded; one
'bash install.sh --resume' re-verified all 12 phases and produced the
report). Air-gapped single-node was proven on 18.09 with v0.5.7.

Surviving interruptions
- The installer offers to run inside a screen session and explains why;
  running ./install.sh again after a lost connection offers to reattach.
- The SSH connections the installer opens to the nodes send keep-alives
  (15 s) and are retried up to 3 times when the connection itself drops
  (exit 255). A failing remote command is never retried.
- Every finished phase is a checkpoint in .install-state.json; --resume
  re-verifies existing VMs, disks, firewall rules, kernel settings, mounts
  and stanctl instead of recreating them, and skips a completed stanctl up.
- Firewall resume adopts rules created earlier without a deployment
  identity and compares ports per protocol (GCP stores tcp:80,tcp:443,
  tcp:8443 as three entries); it offers to refresh the SSH source range
  when the operator's public IP changed.
- The final report (UI URL, node IP, hosts-file line) is saved to
  .install-report.txt, re-printed after the screen session ends, held on
  Enter inside screen, and available any time with 'bash install.sh
  --report' or the start menu.

Always visible progress
- An animated spinner with the step label and elapsed time turns every
  second on every remote command, gcloud call, package copy, SSH wait and
  reboot wait, so no step is ever silent; each output line pushes it down.
- Percent and elapsed time while the air-gapped archive is inspected;
  countdowns for fixed waits.

Always a next step
- Every known failure ends in a HOW TO RESOLVE box with exact commands
  (VM/disk conflicts, firewall mismatches, missing companion files, legacy
  state, missing package space, ...).
- Any other failure (set -e) prints the failing remote command and node,
  the log path and the exact --resume command instead of a bare prompt.

Guided input
- Empty or invalid input re-asks; cancelling requires confirmation.
- Every question is preceded by a short explanation; secrets are masked
  with • per character; keys are asked in the order download → agent →
  sales; GCP project defaults to instana-support-test-account; region and
  zone default from this machine's own GCE zone.
- Start menu: install, dry-run, resume, destroy or clean up (by VM name,
  zone auto-discovered, only the installer's own resources, typed
  confirmation), show report, exit. --dry-run, --resume, --destroy,
  --report, --help.
- Air-gapped: guided menu (existing archive / build here with stanctl and
  backend version choice / switch to online), single-pass archive check,
  ≥20 GB output space check, package build retried 3 times reusing images
  already exported.

Fixes
- Three-node start misread its own phase-1 checkpoint as an existing
  deployment.
- Three-node resume phase 10: dpkg-query format was expanded on the node,
  and the stanctl status is "hold ok installed" (apt-mark hold), so every
  resume stopped there.
- Heartbeat counter '(( i++ ))' under set -e ended the heartbeat after one
  tick and could end the installer.
- destroy.sh refused state files without resources and reports DELETED /
  MISSING honestly; clean-up filters are quoted regexes; boot disks are
  skipped.
- Reachability probe accepted only 2xx; any HTTP answer now counts.
- gnupg installed before the key, keyring 0644, APT list written only after
  the key.

Details per step are in IZMENE_v0.5.7.txt, IZMENE_v0.5.8.txt and
IZMENE_v0.5.9.txt.

Known gaps (next)
- Resume for air-gapped installs; three-node air-gapped end-to-end test.
- Version choice offered on every start; cost guard for idle labs.
