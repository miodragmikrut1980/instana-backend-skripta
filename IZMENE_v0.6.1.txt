v0.6.1 — backend version is chosen first (urgent-ticket use case)

Why: when an urgent ticket arrives, the lab must run exactly the customer's
backend version. Until now the online path asked for the version in phase 10,
about 20 minutes into the run, after the VM and disks were already created.

- Online mode now asks for the stanctl and backend version right after the
  license keys, before anything is created on GCP. The exact stanctl package
  is installed on the management machine from the authenticated repository
  and 'stanctl versions identify' lists the backend versions it supports; the
  chosen pair is pinned for the whole run (shown in the plan, used by phase
  10 on the VM, written into the final report and .install-report.txt).
- If the management machine cannot do that (not Ubuntu/Debian, no sudo,
  repository unreachable, wrong download key) the installer says so and the
  version is chosen on the Instana VM in phase 10, exactly as before.
- Resume keeps the versions recorded in .install-state.json; air-gapped takes
  them from the archive, unchanged.
- The screen hint no longer claims "1-2 hours": a single-node online run is
  30-40 min; three-node and air-gapped take longer.

2026-10-15 — x86-64-v3 CPU requirement
- IBM raised the minimum supported CPU architecture from x86-64-v2 to
  x86-64-v3. Phase 6 now verifies on every node (single-node and both
  three-node paths) that the CPU provides the v3 instruction set (avx, avx2,
  bmi1, bmi2, f16c, fma, abm/lzcnt, movbe, xsave on top of v2) before
  anything is installed. A node that lacks them stops with a HOW TO RESOLVE
  box naming the missing flags, the CPU model, and the gcloud commands to
  move the VM to an n2/Cascade Lake platform, then --resume. n2-standard
  machine types, which the installer uses, provide x86-64-v3.

2026-10-15 — run time is measured and shown
- Every phase prints how long it took and how long the run has been going
  ("Phase 7 took 4m 12s; running for 18m 03s since start (…)").
- The checklist shows each completed phase's duration, also for phases
  completed in an earlier run (durations are kept in .install-state.json).
- The final summary, the final report and .install-report.txt carry
  "Total time: this run … ; all phases together …" — the second figure is
  the real installation work time across resumes.
- A stop (error or unexpected failure) says how long the run lasted.
- The /etc/hosts lines in the final report (screen and .install-report.txt)
  start at column 1, so a block copy pastes cleanly into the hosts file.

2026-10-15 — air-gapped resume (single-node and three-node)
- Why: an interrupted air-gapped run had to copy the tens-of-GB package
  again, and a three-node air-gapped deployment could not be resumed at all
  (it used an older flow without deployment identity; --resume stopped on
  "VM already exists").
- Phase 10 copies the package to /var/tmp/instana-airgapped.tar.gz on the
  VM (kept across a reboot, unlike /tmp) under a .part name and renames it
  when the transfer finished. Before copying it removes leftovers (also the
  /tmp copy older releases left after a failed import) and requires free
  space of about twice the package plus 5 GB in /var/tmp (package plus 5 GB
  when an existing copy is reused); too little stops with HOW TO RESOLVE,
  an unreadable df only warns.
- An existing copy, or a .part of full size (transfer finished, rename
  lost), is compared by SHA-256 with the local archive and reused; anything
  else is replaced.
- The import is never retried automatically (it is not idempotent) and runs
  under a lock on the VM (stanctl's children do not inherit the lock). When it succeeds the VM gets a marker
  /var/lib/instana-airgap/imported (backend, stanctl, package size), then
  the state is saved, and only then the copy is deleted as a separate step.
  A lost connection or failed import stops with HOW TO RESOLVE; the copy
  stays and --resume imports again from it without a new transfer.
- A finished import (marker plus the exact stanctl version on the VM, not a
  substring match) is not repeated, even if the connection dropped before
  the local state was written; an empty or different stanctl version
  imports again from the kept copy. A VM marker for a different package
  stops instead of importing over it.
- Every probe of the VM (marker, copy size, checksum) distinguishes "not
  there" from "could not ask": a failed SSH probe stops with HOW TO RESOLVE
  instead of copying tens of GB again or importing twice.
- If the local archive was replaced with another stanctl/backend version
  after the import, the run stops with HOW TO RESOLVE: checked when the
  parameters are loaded, when a three-node resume is validated (also when
  resume was chosen at the "existing state" question), and in phase 10.
- Known errors now end in HOW TO RESOLVE: invalid saved package, changed
  three-node parameters during resume (both checks), a 'stanctl up' with
  uncertain outcome on three-node resume, wrong stanctl after import.
- Three-node air-gapped now uses the same verified three-node lab flow as
  online (3x n2-standard-16, deployment identity and labels, per-deployment
  firewall rules, root SSH, resume of every phase); phase 10 imports the
  package on node0. The old three-node flow was removed. The plan shows
  n2-standard-16 for three-node, the size question says only small is
  supported, and three-node air-gapped notes that phase 6 still uses apt.
  End-to-end on GCP still to be confirmed.
- New test: test-airgap-resume.sh (16 cases, incl. space thresholds, probe
  failures, empty stanctl output, marker contents).
