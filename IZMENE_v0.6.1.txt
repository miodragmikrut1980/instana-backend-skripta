v0.6.1 — backend version is chosen first (urgent-ticket use case)

Why: when an urgent ticket arrives, the lab must run exactly the customer's
backend version. Until now the online path asked for the version in phase 10,
about 20 minutes into the run, after the VM and disks were already created.

- Online mode now asks for the stanctl and backend version right after the
  license keys, before anything is created on GCP. The exact stanctl package
  is installed on the management machine from the authenticated repository
  and 'stanctl versions identify' lists the backend versions it supports; the
  chosen pair is pinned for the whole run (shown in the plan, used by phase
  10 on the VM, written into the final report and .install-report.txt).
- If the management machine cannot do that (not Ubuntu/Debian, no sudo,
  repository unreachable, wrong download key) the installer says so and the
  version is chosen on the Instana VM in phase 10, exactly as before.
- Resume keeps the versions recorded in .install-state.json; air-gapped takes
  them from the archive, unchanged.
- The screen hint no longer claims "1-2 hours": a single-node online run is
  30-40 min; three-node and air-gapped take longer.

2026-10-15 — x86-64-v3 CPU requirement
- IBM raised the minimum supported CPU architecture from x86-64-v2 to
  x86-64-v3. Phase 6 now verifies on every node (single-node and both
  three-node paths) that the CPU provides the v3 instruction set (avx, avx2,
  bmi1, bmi2, f16c, fma, abm/lzcnt, movbe, xsave on top of v2) before
  anything is installed. A node that lacks them stops with a HOW TO RESOLVE
  box naming the missing flags, the CPU model, and the gcloud commands to
  move the VM to an n2/Cascade Lake platform, then --resume. n2-standard
  machine types, which the installer uses, provide x86-64-v3.

2026-10-15 — run time is measured and shown
- Every phase prints how long it took and how long the run has been going
  ("Phase 7 took 4m 12s; running for 18m 03s since start (…)").
- The checklist shows each completed phase's duration, also for phases
  completed in an earlier run (durations are kept in .install-state.json).
- The final summary, the final report and .install-report.txt carry
  "Total time: this run … ; all phases together …" — the second figure is
  the real installation work time across resumes.
- A stop (error or unexpected failure) says how long the run lasted.
- The /etc/hosts lines in the final report (screen and .install-report.txt)
  start at column 1, so a block copy pastes cleanly into the hosts file.
